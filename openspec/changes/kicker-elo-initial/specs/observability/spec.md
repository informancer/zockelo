## ADDED Requirements

### Requirement: Application exposes a health check endpoint for internal use
The system SHALL expose a `GET /health` endpoint that verifies connectivity to Postgres (both Ecto repo and EventStore) and returns a JSON response. The endpoint is used exclusively by the Docker `HEALTHCHECK` instruction (which runs `curl -f http://localhost:4000/health` inside the container) and by Prometheus/Grafana probing within the Docker internal network.

**`/health` SHALL NOT be publicly accessible.** Caddy SHALL NOT proxy `/health` to external callers. No host port mapping exists for this endpoint. Operators needing an external uptime probe (e.g. UptimeRobot) SHALL monitor `GET /:tenant_slug/login` instead, which returns 200 for any valid tenant slug without revealing sensitive data.

The response body SHALL contain only `{"status": "ok"}` or `{"status": "error", "reason": "database_unavailable"}` — no version or build information.

#### Scenario: All dependencies healthy
- **WHEN** `GET /health` is called from within the Docker network
- **THEN** the response is `200 OK` with body `{"status": "ok"}`

#### Scenario: Database unreachable
- **WHEN** `GET /health` is called and Postgres is not reachable
- **THEN** the response is `503 Service Unavailable` with body `{"status": "error", "reason": "database_unavailable"}`

#### Scenario: /health not reachable from public internet
- **WHEN** the application is deployed with the default docker-compose and Caddy configuration
- **THEN** `GET /health` is not accessible from outside the Docker network; Caddy does not proxy this path

### Requirement: Every request carries a unique correlation ID
The application SHALL add `Plug.RequestId` to the endpoint pipeline. This generates a unique `X-Request-Id` header for every request and includes it in all log entries for that request. The ID is propagated through LiveView mounts so that log lines for a single user action can be correlated across the structured log output.

#### Scenario: Log lines for a request share a request ID
- **WHEN** a request is processed
- **THEN** every log line emitted during that request contains the same `request_id` field

### Requirement: Application emits structured JSON logs
All application log output SHALL be formatted as JSON (via `logger_json` or equivalent). Log level in production SHALL default to `:info`. The following events SHALL be logged explicitly at `:info` level:

- Successful player authentication (player_id, tenant_id — no email or name)
- Magic link token issued (tenant_id only — no email)
- Failed authentication attempt (reason, tenant_id — no email)
- Oban job failures (job name, error)
- Projection errors (event type, error)
- Admin actions (actor_id, action — mirrors audit log)

The following SHALL never appear in logs (per security spec):
- PII (names, emails)
- Token values (magic links, session tokens, invite tokens)
- Encryption keys

#### Scenario: Log output is valid JSON
- **WHEN** the application emits a log message
- **THEN** each log line is a valid JSON object containing at minimum: `timestamp`, `level`, `message`

#### Scenario: Authentication event logged without PII
- **WHEN** a player successfully authenticates
- **THEN** a log entry is written containing player_id and tenant_id but no name or email

### Requirement: Observability tools are operator-only and not accessible to application users
The observability stack (Prometheus, Grafana, GlitchTip) is intended exclusively for the **operator** — the person running the server infrastructure. These tools are not part of the application's user-facing interface and SHALL NOT be accessible to super admins, tenant admins, or players through any in-app feature.

Access control per component:

- **`/metrics`** — SHALL NOT be mapped to a host port. Prometheus scrapes it container-to-container within the Docker network. It is unreachable from outside the host.
- **`/health`** — accessible only within the Docker internal network (container-to-container). Caddy does not proxy it externally. No host port mapping exists.
- **Grafana (port 3000)** — SHALL be bound to `127.0.0.1` in `docker-compose.yml` (i.e. `127.0.0.1:3000:3000`), making it accessible only from localhost. Operators access it via SSH tunnel (`ssh -L 3000:localhost:3000 user@host`). The Grafana admin password is set via `GF_SECURITY_ADMIN_PASSWORD` generated by `setup.sh`; no manual first-login password change is required.
- **GlitchTip (port 1337)** — same localhost-binding approach as Grafana. First-time setup (superuser creation, project creation, DSN retrieval) is automated by `setup.sh --full` via the GlitchTip HTTP API; `GLITCHTIP_DSN` is written to `.env` automatically. No manual browser-based setup is required.
- **Prometheus (port 9090)** — SHALL also be bound to `127.0.0.1`; it is an internal data source for Grafana and not intended for direct operator use in normal operation.

Operators who prefer a different access model (e.g. exposing Grafana through a subdomain behind a reverse proxy with authentication) MAY do so, but this is not the default configuration.

#### Scenario: /metrics not reachable from public internet
- **WHEN** the application is deployed with the default docker-compose configuration
- **THEN** `GET /metrics` is not accessible from outside the Docker network; no host port mapping exists for it

#### Scenario: Grafana accessible only from localhost by default
- **WHEN** an operator runs `docker-compose --profile monitoring up`
- **THEN** Grafana listens on `127.0.0.1:3000` and is not reachable from external IP addresses; the operator accesses it via SSH tunnel

#### Scenario: Application users have no access to observability tools
- **WHEN** a super admin, tenant admin, or player is authenticated in the application
- **THEN** there is no link, button, or API endpoint in the application that exposes Prometheus metrics, Grafana dashboards, or GlitchTip data

### Requirement: Application exposes Prometheus metrics via PromEx
The system SHALL use PromEx to expose Prometheus-compatible metrics at `GET /metrics` (reachable only within the Docker internal network — no host port mapping). The following metric groups SHALL be enabled:

- **Phoenix metrics**: HTTP request duration and count by route and status
- **LiveView metrics**: mount duration, handle_event duration, socket count
- **Ecto metrics**: query duration by repo and query name
- **Oban metrics**: job execution duration, queue depth, failure count by worker
- **VM metrics**: BEAM memory usage, process count, scheduler utilisation
- **EventStore metrics**: event write/read latency (custom telemetry events)

#### Scenario: Metrics endpoint returns Prometheus format
- **WHEN** `GET /metrics` is called from within the internal network
- **THEN** the response contains valid Prometheus text format metrics

### Requirement: Grafana provides pre-built dashboards
The docker-compose setup SHALL include a Grafana instance pre-configured with Prometheus as a data source and the following dashboards provisioned automatically:

- **Application overview**: request rate, error rate, p95 latency by route
- **LiveView**: active socket count, mount/event latency
- **Oban jobs**: job throughput, failure rate, queue depth by worker
- **Database**: Ecto query latency, slow query count
- **BEAM VM**: memory, processes, scheduler load

#### Scenario: Grafana dashboards available on first boot
- **WHEN** `docker-compose --profile monitoring up` is run for the first time
- **THEN** Grafana is accessible with all dashboards pre-provisioned (no manual setup required)

### Requirement: Grafana alerting rules notify operators of critical conditions
The Grafana provisioning SHALL include a default alert rule set covering the most critical failure modes. Alerts SHALL be provisioned automatically alongside dashboards and require no manual configuration. The following alert rules SHALL be provided:

- **Health check failing**: `/health` (probed by Grafana via Docker internal network) returns non-200 for more than 1 minute
- **HTTP error rate spike**: 5xx response rate exceeds 5% of requests over a 5-minute window
- **Oban job failure rate**: more than 10 job failures per minute across all queues
- **High memory usage**: Phoenix app process exceeds 200MB RAM

Alert notifications SHALL be sent to a configurable contact point (email or webhook URL), configured via `GRAFANA_ALERT_EMAIL` or `GRAFANA_WEBHOOK_URL` environment variables. When neither is set, alerts are visible in the Grafana UI only.

#### Scenario: Operator is notified when health check fails
- **WHEN** the `/health` endpoint returns non-200 for over 1 minute
- **THEN** Grafana fires the health check alert to the configured contact point

#### Scenario: Alerts visible in UI when no contact point configured
- **WHEN** neither `GRAFANA_ALERT_EMAIL` nor `GRAFANA_WEBHOOK_URL` is set
- **THEN** alerts fire and are visible in the Grafana Alerting panel but no external notification is sent

### Requirement: Runtime errors are captured by GlitchTip
The system SHALL integrate with GlitchTip (Sentry-compatible, self-hosted) using the `sentry` Elixir hex package. All unhandled exceptions and error-level log events SHALL be captured with stack traces. The GlitchTip DSN SHALL be configured via environment variable (`GLITCHTIP_DSN`). When `GLITCHTIP_DSN` is not set, error tracking SHALL be silently disabled (no startup failure).

#### Scenario: Unhandled exception captured
- **WHEN** an unhandled exception occurs in a LiveView or controller
- **THEN** the exception and stack trace are sent to GlitchTip; the user sees a generic error page

#### Scenario: Error tracking disabled when DSN not configured
- **WHEN** `GLITCHTIP_DSN` environment variable is not set
- **THEN** the application starts normally and silently skips error reporting

### Requirement: Oban workers are assigned to named queues with explicit concurrency
All Oban workers SHALL be assigned to one of three named queues to ensure time-sensitive jobs are never starved by bulk background work and to enable accurate per-queue metrics in Grafana:

| Queue | Concurrency | Workers |
|---|---|---|
| `notifications` | 10 | All notification email workers |
| `scheduled` | 5 | `GameConfirmationWorker`, `InactiveAccountWarningWorker`, `InactiveAccountDeletionWorker`, `ExpiredInviteCleanupWorker`, `StaleRecordCleanupWorker` |
| `critical` | 2 | `TenantDeletionWorker` |

The `notifications` queue has higher concurrency to handle bursts of emails (e.g. a maintenance broadcast to all tenants). The `critical` queue is low-concurrency but is never blocked by high-volume jobs in other queues.

#### Scenario: Notification jobs not starved by cleanup burst
- **WHEN** a large number of stale-record cleanup jobs are running
- **THEN** notification jobs on the `notifications` queue are not delayed because they run on a separate queue

### Requirement: Resource efficiency is an explicit goal
The application SHALL be deployable on a 2GB RAM VPS running the full stack (app + Postgres + Prometheus + Grafana + GlitchTip + Redis). The Phoenix application process SHALL use no more than 150MB RAM under normal load. No unnecessary dependencies SHALL be added.

Target deployment footprints:

| Profile    | Services                              | Target RAM |
|------------|---------------------------------------|------------|
| Minimal    | app + postgres                        | ~400MB     |
| Monitoring | + prometheus + grafana                | ~900MB     |
| Full       | + glitchtip + redis                   | ~1.8GB     |

#### Scenario: App process stays within memory target
- **WHEN** the application is running under normal load (up to 50 concurrent users)
- **THEN** the Phoenix application process uses no more than 150MB RAM

### Requirement: Docker Compose deployment is provided
The repository SHALL include a `docker-compose.yml` with compose profiles for incremental deployment. A `.env.example` file SHALL document all required and optional environment variables. The setup SHALL require no manual steps beyond running `setup.sh` (or `setup.sh --full` for the full stack). `setup.sh` generates all secrets, configures Grafana admin credentials, and (in `--full` mode) automates GlitchTip project and DSN setup via the GlitchTip HTTP API.

Profiles:
- *(default)*: app + postgres
- `monitoring`: adds prometheus + grafana (pre-provisioned dashboards)
- `full`: adds glitchtip + redis

#### Scenario: Minimal deployment requires only Docker and running setup.sh
- **WHEN** an operator runs `./setup.sh` and answers the prompts
- **THEN** the application is fully functional with no additional configuration steps

#### Scenario: Full deployment requires no manual observability configuration
- **WHEN** an operator runs `./setup.sh --full`
- **THEN** Grafana is accessible with a generated admin password (printed at end of setup), GlitchTip is accessible with generated admin credentials, and `GLITCHTIP_DSN` is written to `.env` automatically; no browser-based first-time setup is required

#### Scenario: Monitoring profile adds observability with no extra config
- **WHEN** an operator runs `docker-compose --profile monitoring up`
- **THEN** Prometheus scrapes the `/metrics` endpoint and Grafana dashboards are available at port 3000

### Requirement: Grafana and GlitchTip first-time setup is automated by setup.sh
Manual browser-based first-time configuration for Grafana and GlitchTip is eliminated. `setup.sh` SHALL handle both:

**Grafana:**
- `setup.sh` generates a random `GRAFANA_ADMIN_PASSWORD` (32 bytes, base64url-encoded) and writes it to `.env`
- `docker-compose.yml` passes this as `GF_SECURITY_ADMIN_PASSWORD` to the Grafana container
- Grafana starts with the operator-chosen password already set; no "change default password" step is needed
- `setup.sh` prints the Grafana admin credentials (username: `admin`, password: generated value) at the end of setup, with an SSH tunnel command for access

**GlitchTip** (only when `--full` profile is selected):
- `setup.sh` generates `GLITCHTIP_SUPERUSER_EMAIL` and `GLITCHTIP_SUPERUSER_PASSWORD`, writes both to `.env`
- `docker-compose.yml` passes these to the GlitchTip container; GlitchTip creates the superuser automatically on first start
- After containers are healthy, `setup.sh` calls the GlitchTip HTTP API to:
  1. Obtain an auth token (POST `/api/v0/auth/login/`)
  2. Create an organization named after `APP_NAME` (POST `/api/v0/organizations/`)
  3. Create a project named `zockelo` (POST `/api/v0/teams/{team}/projects/`)
  4. Retrieve the DSN (GET `/api/v0/projects/{org}/{project}/keys/`)
  5. Write the DSN value to `GLITCHTIP_DSN` in `.env` and restart the app container
- `setup.sh` prints the GlitchTip admin URL and credentials at the end of setup

If the GlitchTip API calls fail (e.g. container not yet healthy after timeout), `setup.sh` SHALL print a warning with manual fallback instructions rather than failing the entire setup.

#### Scenario: Grafana admin password is set without manual intervention
- **WHEN** `setup.sh` is run and `--profile monitoring` or `--full` is selected
- **THEN** `GRAFANA_ADMIN_PASSWORD` in `.env` is populated with a generated value; Grafana starts with that password already set; `setup.sh` prints the credentials

#### Scenario: GlitchTip project and DSN are created automatically
- **WHEN** `./setup.sh --full` is run for the first time
- **THEN** `setup.sh` creates the GlitchTip superuser, creates a project, retrieves the DSN, and writes it to `GLITCHTIP_DSN` in `.env`; no manual browser steps are required

#### Scenario: GlitchTip API failure is non-fatal
- **WHEN** the GlitchTip container fails to become healthy within the wait timeout during `setup.sh --full`
- **THEN** `setup.sh` prints a warning explaining the manual steps to retrieve the DSN, and exits successfully; the application still starts
